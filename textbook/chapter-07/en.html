Chapter 07 · Module 2 · Week 7

Convolutional Neural Networks for Computer Vision

Chapter 5 built a training loop and Chapter 6 taught you to distrust a single number. This chapter is about a different kind of decision: not which optimiser, but which architecture, and what that architecture costs. The spine of the week is deliberately not "the CNN is more accurate" — on this data the numbers do not say that. They say something narrower and more useful: a two-layer convolution with 1,898 parameters reaches 0.9808, while a fully connected network with 17,226 parameters reaches 0.9785, and the 0.0023 gap is smaller than one standard deviation. So we spend the chapter on the arithmetic that makes that possible — the sliding dot product, the output-size formula checked against real tensors, the receptive field recurrence 3 → 4 → 8 → 10 — and then on the two places where the honest answer is not the convenient one: pooling is a design choice worth 4.1 points, and augmentation buys 29 points of robustness and pays 3 points of clean accuracy. The chapter closes with a confusion matrix over 1,350 test predictions, a measurement of peak memory against batch size, and the four gradient-accumulation weightings that do and do not reproduce a true large batch.

7.1 From Dense Layers to Convolution

The natural first idea is the one Chapter 5 already used: take the image, flatten it into a vector, and hand it to a multilayer perceptron. On an 8x8 digit that vector has 64 entries and the idea works fine. On a photograph it does not, and the reason is arithmetic rather than philosophical — so it can be counted.

7.1.1 Why an Image Cannot Simply Be Flattened

Three separate things go wrong the moment the pixels are laid out in a single row, and each of them has a number attached in this week's experiment.

The parameter count explodes

A dense layer that maps 64 inputs to 128 outputs already holds 64 x 128 + 128 = 8,320 weights. The full network used as this week's control has 17,226 parameters. Scale the input to a real photograph — 224 x 224 x 3 pixels is 150,528 inputs — and a single hidden layer of the same width needs more than 19 million weights before the first ReLU. The growth is quadratic in the image side, and it is the input dimension, not the number of classes, that drives it.

Flattening destroys the layout

Once the 8x8 grid is a 64-long vector, two pixels that were neighbours and two pixels on opposite sides of the image are the same kind of object: two indices. Nothing in a dense layer's weight matrix knows that index 8 and index 9 were adjacent on the same row and that index 0 was a whole row away. The spatial structure that actually carries the information in an image is thrown away before learning begins.

A shift is treated as a brand-new object

A dense network has to learn every pattern once per position. This is not a theoretical complaint; it is measured. Shifting the test images by one column costs the dense network heavily: its accuracy falls from 0.9785 at zero shift to 0.5089 at one column, while the convolution falls only to 0.6481. The same digit, moved one pixel, is half a new problem for the network that cannot share weights across positions.

7.1.2 Local Connectivity and Weight Sharing

A convolution layer answers all three problems with two structural assumptions. Local connectivity says that one output value is computed from a small patch of the input — a 3x3 window, not the whole image — so the number of weights per output does not grow with the image size. Weight sharing says that the same small kernel is applied at every position, so the total number of weights depends only on the kernel size and the channel counts, not on how wide the image is.

Those two decisions are what turn "learn a detector for every position" into "learn one detector and slide it". The price is an assumption: that a useful pattern is local and that the same pattern is useful wherever it appears. When that assumption holds — as it does for the stroke of a handwritten digit — the saving is enormous. When it does not, a convolution can be worse than a dense layer, and that is a real cost, not a footnote.

7.1.3 The Parameter Ledger: 17,226 to 1,898

The official teaching plan asks for the parameter comparison explicitly, because it is the cleanest way to see what weight sharing buys. Both architectures below are trained on exactly the same data, with the same split and the same optimiser.

  • Data. sklearn.datasets.load_digits — 8x8 greyscale handwritten digits, 10 classes, 1,797 images, shipped with scikit-learn. import torch, torch.nn as nn
from sklearn.datasets import load_digits
from sklearn.model_selection import train_test_split


def load_split(seed=42):
    """1797 digits, 8x8, scaled to [0, 1]; stratified 70 / 15 / 15."""
    X, y = load_digits(return_X_y=True)          # 8x8 pixels, 10 classes
    X = (X / 16.0).astype("float32")              # pixel range 0..16 -> 0..1
    Xtr, Xrest, ytr, yrest = train_test_split(
        X, y, test_size=0.30, stratify=y, random_state=seed)
    Xva, Xte, yva, yte = train_test_split(
        Xrest, yrest, test_size=0.50, stratify=yrest, random_state=seed)
    t = lambda a: torch.tensor(a)
    return (t(Xtr), t(ytr), t(Xva), t(yva), t(Xte), t(yte))


class MLP(nn.Module):
    """Flatten 64 -> 128 -> 64 -> 10  =  17,226 parameters."""
    def __init__(self):
        super().__init__()
        self.net = nn.Sequential(nn.Linear(64, 128), nn.ReLU(),
                                 nn.Linear(128, 64), nn.ReLU(),
                                 nn.Linear(64, 10))

    def forward(self, x):
        return self.net(x.view(x.shape[0], -1))


class CNN(nn.Module):
    """conv(1->8,3,pad1) ReLU maxpool2 -> conv(8->16,3,pad1) ReLU maxpool2 -> FC 10
    = 1,898 parameters. `pool` is a constructor argument so the average-pooling
    arm can share exactly this code."""
    def __init__(self, pool=nn.MaxPool2d, in_size=8):
        super().__init__()
        self.in_size = in_size
        self.body = nn.Sequential(
            nn.Conv2d(1, 8, 3, padding=1), nn.ReLU(), pool(2, stride=2),
            nn.Conv2d(8, 16, 3, padding=1), nn.ReLU(), pool(2, stride=2))
        self.head = nn.Linear(16 * 2 * 2, 10)      # flatten 64 -> 10

    def forward(self, x):
        x = self.body(x.view(-1, 1, self.in_size, self.in_size))
        return self.head(x.view(x.shape[0], -1))


for m in (MLP(), CNN()):
    print(sum(p.numel() for p in m.parameters()))   # 17226, then 1898
Key terms
  • Convolution — a layer that computes each output from a local patch, using one shared kernel across all positions.
  • Feature map — the 2-D array a convolution produces; one map per output channel.
  • Local connectivity — each output depends on a small neighbourhood of the input.
  • Weight sharing — the same kernel weights are reused at every spatial position, which is what makes the parameter count independent of image width.
  • Translation equivariance — shifting the input shifts the feature map by the same amount; the property a dense layer must learn from scratch at every position; the word here is equivariance, not invariance, because the response moves with the input.

7.2 The Convolution Operation

All of the arithmetic in a convolution is one sentence: take a patch, multiply it element-wise by the kernel, and sum. Everything else — stride, padding, channels, groups — is bookkeeping around that sentence. Writing the sentence once by hand is what makes the vocabulary concrete.

7.2.1 A Sliding Dot Product

The hand-written version below is not the code you will ship; it is the code that makes feature map, stride and padding mean something. It is checked against nn.Conv2d with an assertion, so that "the hand-written version matches PyTorch" is a fact the program verifies, not a claim in a textbook.

import torch, torch.nn as nn
import torch.nn.functional as F


def conv2d_naive(img, kernel, stride=1, pad=0):
    """img: (H, W)  kernel: (kh, kw)  ->  one sliding dot product."""
    H, W = img.shape
    kh, kw = kernel.shape
    if pad:
        img = F.pad(img, (pad,) * 4)
        H, W = H + 2 * pad, W + 2 * pad
    oh = (H - kh) // stride + 1
    ow = (W - kw) // stride + 1
    out = torch.zeros(oh, ow)
    for i in range(oh):
        for j in range(ow):
            patch = img[i * stride:i * stride + kh,
                        j * stride:j * stride + kw]
            out[i, j] = (patch * kernel).sum()
    return out


torch.manual_seed(0)
img, kernel = torch.randn(8, 8), torch.randn(3, 3)
mine = conv2d_naive(img, kernel, stride=1, pad=1)

conv = nn.Conv2d(1, 1, 3, stride=1, padding=1, bias=False)
conv.weight.data = kernel.view(1, 1, 3, 3)
ref = conv(img.view(1, 1, 8, 8))[0, 0]

assert mine.shape == ref.shape == (8, 8)          # padding=1 keeps the size
assert torch.allclose(mine, ref, atol=1e-5)
print("hand-written == nn.Conv2d")

7.2.2 Many Inputs, Many Kernels, Many Outputs

A real layer is not one kernel over one channel. With C_in input channels and C_out kernels, each output channel is produced by its own kernel that spans all input channels. The layer's parameter count is therefore k * k * C_in * C_out + C_out, the first term covering the weights and the second the bias.

# 3 input channels, 16 filters of size 3x3, padding 1 -> 16 output channels
conv = nn.Conv2d(in_channels=3, out_channels=16, kernel_size=3, padding=1)
x = torch.randn(4, 3, 8, 8)                       # a batch of 4 images
y = conv(x)
print(y.shape)                                     # torch.Size([4, 16, 8, 8])
print(sum(p.numel() for p in conv.parameters()))    # 3*3*3*16 + 16 = 448

This is the exact formula that produced the 80 and 1,168 in Section 7.1.3: conv1 = 3*3*1*8 + 8 = 80 and conv2 = 3*3*8*16 + 16 = 1,168.

7.2.3 What an Output Channel Means

Each output channel is one learned feature detector applied across the whole image, and its feature map says where that detector fired strongly. With 8 output channels you get 8 maps, each 8x8; with 16 you get 16. The number of channels is thus the number of distinct patterns the layer is allowed to look for, and it is independent of the image size — the same 3x3 kernel is used whether the input is 8x8 or 1024x1024.

Key terms
  • Kernel (filter) — the small weight tensor that is slid over the input; one kernel produces one output channel.
  • Sliding dot product — the operation itself: element-wise multiply the patch by the kernel, then sum to one number.
  • Input / output channel — the depth of the input volume, against the number of kernels, which becomes the depth of the output.
  • Bias — one learned scalar per output channel, added to every position of that channel's map.

7.3 Stride, Padding, and the Output-Size Formula

Shape errors are the most common failure in deep learning, and they are also the cheapest to eliminate, because they are pure arithmetic. One formula covers a convolution, a pooling layer and a strided convolution alike:

out = (in + 2p - k) / s + 1

where in is the input side, k the kernel size, s the stride and p the padding on each side (integer division). The same four common cases cover almost everything you will write:

kspOutput from an 8x8 inputWhen you use it
3118Same-size convolution; the workhorse of every CNN.
3106Valid convolution; shrinks by k - 1.
2204Pooling: halve the map, double the receptive-field jump.
3214Strided convolution: a learned downsample.

7.3.1 The Formula, Checked Against Real Tensors

The script does not estimate these shapes; it computes them and then compares against the actual forward pass, asserting equality at every stage. The result is the shape chain of this week's CNN: 8x8 -> conv+P -> 8x8 -> pool -> 4x4 -> conv+P -> 4x4 -> pool -> 2x2 -> flatten 64 -> FC 10.

def out_size(size, k, s, p):
    return (size + 2 * p - k) // s + 1


stages = [("conv", 3, 1, 1), ("pool", 2, 2, 0),
          ("conv", 3, 1, 1), ("pool", 2, 2, 0)]
size = 8
for kind, k, s, p in stages:
    size = out_size(size, k, s, p)
    print(kind, "->", size)          # conv -> 8, pool -> 4, conv -> 4, pool -> 2
print("flatten =", 16 * 2 * 2)       # 64

# the same numbers, read off a real forward pass instead of the formula
h = torch.zeros(1, 1, 8, 8)
with torch.no_grad():
    for layer in CNN().body:
        h = layer(h)
        print(tuple(h.shape[1:]))     # (8,8,8) (8,8,8) (8,4,4) (16,4,4) (16,2,2)

All four formula checks match the forward pass exactly. When a shape mismatch error fires, the productive first move is to run this arithmetic by hand rather than to edit the code — most shape errors are located here in one minute.

Key terms
  • Stride — how far the kernel moves between positions; a stride of 2 halves the output side.
  • Padding — zeros added around the border so that the kernel can centre on edge pixels; padding 1 with a 3x3 kernel keeps the size unchanged.
  • Output-size formula — out = (in + 2p - k)/s + 1, shared by convolution and pooling.
  • Flatten dimension — channels x height x width at the end of the convolutional body, 64 here, which becomes the input width of the linear head.

7.4 Receptive Field

The receptive field of a unit is how much of the original input it can see. It is the number that tells you whether your network is even capable of relating two distant parts of the image, and it grows faster than intuition suggests once pooling is involved.

7.4.1 The Recurrence

Track two quantities stage by stage: the receptive field rf and the jump, which is the effective distance in input pixels between two neighbouring outputs. Each stage updates them as

rf = rf + (k - 1) * jump    and    jump = jump * s

starting from rf = 1 and jump = 1. A stride-2 pooling layer doubles the jump, which is why the layer after it gains receptive field twice as fast.

The receptive field follows the sequence 3 -> 4 -> 8 -> 10. The row that carries the lesson is Conv 2: receptive field 8, exactly the side of the whole image. On this 8x8 data the second convolution already sees everything there is to see. No amount of extra depth could add translation invariance here, because there is no unexplored region left — that is the data being small, not the model being weak.

def receptive_field(stages, size=8):
    rf, jump = 1, 1
    for kind, k, s, p in stages:
        size = (size + 2 * p - k) // s + 1
        rf = rf + (k - 1) * jump
        jump = jump * s
        print(f"{kind:<4} k={k} s={s}  map {size}x{size}  RF={rf}  jump={jump}")

Key terms
  • Receptive field — the region of the input that influences one unit's value.
  • Jump — the input-space distance between two adjacent outputs of a feature map; multiplied by the stride at each stage.
  • Effective receptive field — the region that actually contributes in practice, which is narrower at the edges of the field than at the centre.

7.5 Pooling

Pooling is usually taught as "downsampling", which is only one of the three jobs it does and the least interesting of them. It also grows the receptive field and it buys tolerance to small shifts — and, crucially, it is a choice with a measured price.

7.5.1 Three Jobs, One Cost

JobWhat it doesWithout it
Shrink the map8x8 -> 4x4 -> 2x2; compute and memory in later layers fall with the areaEvery later layer pays full spatial cost
Grow the receptive fieldA stride-2 pool doubles the jump, so the next conv sees twice as farStacked 3x3 convolutions only reach 3, 5, 7 ...
Tolerate small shifts"A strong response somewhere in this patch" is steadier than "exactly at row 3, column 5"The output moves when the input moves by one pixel

The cost is that pooling throws away position. For a task that needs to know where — segmentation, detection, keypoint localisation — that information has to be restored later. And the choice of which pooling function is not a matter of taste that averages out.

7.5.2 The Pooling Choice Is Worth 4.1 Points

Two architectures below differ in exactly one respect: the pooling function. The channels, kernels, learning rate and epochs are identical, and the parameter count is the same. The result is the clearest "this is a design decision" measurement of the week.

ArchitecturePoolingParametersTrain accVal accTest acc
CNN smallMax pooling1,8980.9987 ± 0.00090.9704 ± 0.01010.9808 ± 0.0084
CNN smallAverage pooling1,8980.9497 ± 0.00890.9289 ± 0.01640.9400 ± 0.0081

Max pooling reaches 0.9808 and average pooling reaches 0.9400. The gap is 4.1 points, several times the standard deviation of either arm, and the two networks have the same number of parameters. Average pooling smooths away the strongest response, and for handwritten digits the discriminative information is exactly where the stroke is densest. Choosing a pooling function is choosing what to keep — and it can be worth more than any amount of hyper-parameter tuning on top of a wrong choice.

Key terms
  • Pooling — a fixed, parameter-free reduction over a small window, used to shrink maps and grow the receptive field.
  • Max pooling — keeps the largest value in each window; preserves the strongest response, at the cost of position detail.
  • Average pooling — keeps the mean of each window; smoother, but it dilutes a single strong response.
  • Global average pooling — averaging each channel to one number, a common replacement for a flatten-plus-dense head.

7.6 What the Classic Architectures Solved

The history of CNN design is a sequence of specific bottlenecks, each fixed by one idea. Read as a list of dates it is trivia; read as a list of problems it is a design vocabulary you will reuse.

ArchitectureThe problem it addressedThe idea it introduced
LeNetCan a network read a digit at all?The template itself: alternating convolution and pooling, then a small dense head. Small, and enough for 8x8-to-32x32 digits; it is essentially this week's model.
AlexNetReal, high-resolution colour images with many classes; training was too slow and overfitted.Go deep and wide, use ReLU instead of saturating activations, and use dropout and data augmentation to hold overfitting back — plus GPUs to make it affordable.
VGGAd-hoc kernel sizes made architectures hard to reason about or reproduce.A uniform recipe: stack only 3x3 convolutions, with pooling between blocks. Depth with a simple, repeatable pattern, and small kernels that keep the parameter cost low.
ResNetBeyond a certain depth, adding layers made training worse, not better.Skip connections: let a block learn a residual around the identity, so gradients can flow through very deep stacks. Depth became usable instead of self-defeating.

Only the ideas are the point here. The graded material of this week is not "implement ResNet"; it is recognizing that each of these four answered a bottleneck that the previous one created, and that the bottleneck is what you look for when a model will not train.

7.7 Data Augmentation

Augmentation presents the model with transformed copies of the training inputs and relies on the label surviving the transform. The precondition is precise and easy to miss: the transform must preserve the label. Flipping a digit horizontally turns a 6 towards a 9; flipping it vertically destroys a 9. A transform that does not preserve the label does not add information — it manufactures incorrectly labelled examples while looking like a sophisticated regulariser.

7.7.1 What This Experiment Augments With

The augmented arm applies a random shift of at most one pixel in each axis, to the training batch only; at test time the images are untouched. The same function is used as the training augmentation and as the test-time probe, so the two are guaranteed comparable.

def shift_batch(imgs, dx, dy):
    """Zero-filled translation of an (n, 1, 8, 8) batch. Used both as the
    training augmentation and as the test-time perturbation."""
    out = torch.roll(imgs, shifts=(dy, dx), dims=(2, 3))
    if dy > 0:   out[:, :, :dy, :] = 0
    elif dy < 0: out[:, :, dy:, :] = 0
    if dx > 0:   out[:, :, :, :dx] = 0
    elif dx < 0: out[:, :, :, dx:] = 0
    return out


# inside the training loop, for the augmented arm only
if arm == "cnn_aug":

The augmentation ledger Bought: +29 points at dx = -1 (0.6481 to 0.9415), and the training curve no longer runs to 1.000 (it sits at 0.9292 at epoch 115), so overfitting is held back.
Paid: -3 points at dx = 0 (0.9808 to 0.9504).
The lesson: augmentation did not raise the ceiling; it flattened the curve. It trades peak clean accuracy for robustness to shifts, and whether that trade is good is a question about your inputs, not about the model. If your users photograph the digit — buy the robustness. If the input is already cropped and aligned — you are paying for nothing.
Key terms
  • Data augmentation — producing transformed copies of the training inputs whose labels are unchanged.
  • Label-preserving transform — a transform the correct label survives; the precondition for augmentation to help.
  • Test-time perturbation — a transformation applied only when measuring, to probe robustness rather than to train.
  • Robustness / clean accuracy trade-off — the measured exchange of accuracy on the untouched test set for accuracy under perturbation.

The matrix sums to 1,350 test predictions (270 x 5), of which 1,324 are correct — an accuracy of 0.9807 — leaving 26 off-diagonal errors. Reading it is a single rule: look off the diagonal. Digit 0 is perfect (135/135); digit 8 is the worst class (124/130, recall 0.9538). Of the 26 errors, 12 involve the digit 8 — about 46.2% of all mistakes — and the worst single class pair is 8 -> 1, which occurs 3 times. Every one of the 26 errors sits on a class pair that is visually close (8 with 1, 8 with 9, 3 with 8); none is a random misread.

import numpy as np
from sklearn.metrics import confusion_matrix

model.eval()
with torch.no_grad():
    y_pred = model(Xte).argmax(1).numpy()

cm = confusion_matrix(yte.numpy(), y_pred)     # rows true, columns predicted
off = cm.copy()
np.fill_diagonal(off, 0)                       # keep only the mistakes
print("errors:", off.sum(), "accuracy:", cm.trace() / cm.sum())
Key terms
  • Arm — one configuration under test, with every other factor of the protocol held fixed.
  • Seed replication — repeating an arm over several seeds so the spread, not one run, is the measurement.
  • Mean ± standard deviation — the reporting form used for every figure here; a single-run value is not a result.
  • Confusion matrix — the table of true class against predicted class; the diagonal counts correct decisions and every off-diagonal cell is a specific confusion.
  • Recall — of the true examples of a class, the fraction the model found; 0.9538 for the worst class here.

7.9 Error Analysis: From the Matrix to the Samples

"Accuracy is 0.98" is not a finding; it is a starting point. Error analysis is the discipline of getting from an aggregate number down to the specific samples the model gets wrong, and then to a hypothesis about why — one that can be tested. It is the deliverable the course's teaching plan asks for explicitly: look at which class of samples the model is actually wrong on.

7.9.1 The Method, in Five Moves

Print the matrix, not just the accuracy

0.9807 hides 26 errors, 12 of which involve the digit 8. The accuracy number mentions none of this; the matrix is where the work starts.

Name the worst class pair, with a count

"8 is read as 1, three times" is a hundred times more useful than "the model does worse on some classes". The count matters because a single occurrence may be noise and three may be a pattern.

Pull out concrete cases, with model probabilities

Not "it got some 8s wrong" but "true 8, predicted 7, confidence 0.9829, probability on the true class 0.0144". The probabilities separate hesitation from a confident error, and the two call for different fixes.

Attach one testable hypothesis per case

"This 6 has a closed lower loop" is a hypothesis, and it is checkable: collect the 6s with closed lower loops and see whether they all become 8. That turns a story into an experiment.

State the next step and how you will judge it

Same split, same metric, one change at a time — the rule that does not change all semester.

The delivery standard for a complete error analysis A report that carries only one aggregate number has not done the work. A complete one contains all of: (1) the confusion matrix itself, printed; (2) the worst class pair, named, with its count; (3) at least three concrete misclassified cases, each with the model's probability on the predicted and true classes; (4) a testable hypothesis for each; and (5) the next experiment and the criterion by which it will be judged. Missing any one of these is the most common way this week's report loses marks.
Key terms
  • Error analysis — moving from an aggregate metric to the specific failures and their causes.
  • Class pair — an ordered (true, predicted) pair; the unit in which confusions are counted.
  • Confidence vs true-class probability — how sure the model was of its (wrong) answer, against how little probability mass the correct class received.
  • Testable hypothesis — a proposed cause stated so that a further measurement could confirm or refute it.

7.10 GPU Memory Management and Green Computing

Running out of memory is the most common blocker in this week's lab, and it is almost never a hardware problem — it is a batch-size problem. The right response is a measurement followed by a specific order of operations, not a purchase order.

7.10.1 Peak Memory Grows with Batch Size

Peak resident memory was measured in a separate process for each batch size, with the input nearest-neighbour upsampled to 32x32 so the effect is measurable at all. The baseline — importing torch and building the model, without training — is 306.5 MB, and everything below is reported as the increment above that baseline.

A measurement trap worth knowing On macOS, ru_maxrss is reported in bytes; on Linux it is in kilobytes. Dividing by the wrong constant silently reports megabytes that are off by a factor of 1024. The probe handles this with / 1024 ** 2, and the raw numbers above were produced with that divisor on macOS.

7.10.2 What to Do When You Run Out of Memory

Work down this list. Each step down costs more; the last two are no longer tuning, they are new hardware or a new plan.

Halve the batch size (free)

Changes memory, not maths. The side effect is noisier gradients, compensated with more steps or a higher learning rate. Do this before suspecting the hardware.

Gradient accumulation (free)

Buy the effective batch back without the memory. Measured below: 4 x 32 with the right weighting reproduces a true batch of 128 exactly. You pay in time, not accuracy.

Mixed precision (cheap, not free)

torch.amp.autocast with a GradScaler halve the activation cost. It changes the numerics, so re-confirm that the metric has not drifted.

Gradient checkpointing or a smaller input (costs)

Trades time for memory, typically 20-30% slower. Shrinking the input resolution changes the task itself, so decide what you are measuring before you change it.

Shrink the model, or admit the task does not fit (last)

Buying a bigger GPU is the last option, not the first. This week's model peaks at 582.0 MB even at batch 1024 and will never run out of memory — measure what you actually need before shopping.

7.10.3 Gradient Accumulation: Buying the Batch Back at the Right Price

Gradient accumulation splits a large effective batch into several small micro-batches, accumulates their gradients, and takes one optimiser step. The effective batch is the micro-batch size times the number of accumulation steps — here 4 x 32 = 128. The test is whether each weighting reproduces a true batch of 128 seed by seed.

WeightingExact formAgreement with the true batch-128 run
exactw = len(sel) / group_size5 / 5 identical
naivew = 1 / accum_steps3 / 5
unscaledno scaling, no reduction2 / 5
noneno scaling, gradients summed directly2 / 5

Only the exact weighting matches on all five seeds. The reason is specific and is worth stating precisely: the difference comes from the last micro-batch group of each epoch having a different size (n_train = 1258 is not divisible by 64 x accum, and in the probe not by 32 x 4 either). Weighting each micro-batch by its share of the group — len(sel)/group_size — is what makes the accumulated gradient equal the group mean; the naive 1/accum_steps form is correct only while every micro-batch has the same size.

An honest boundary on this result The naive and unscaled variants still converge reasonably here because Adam is insensitive to a uniform scaling of the gradient — it normalises by the second moment, so multiplying every gradient by a constant is largely absorbed. That is a property of the optimiser, not a licence to skip the weighting. With SGD the differences would be substantially larger, so the correct conclusion is not "the weighting does not matter", but "with Adam the misweighting is forgiving, and grading it on a different optimiser would expose it". 
# a group of `size` samples split into micro-batches of len(sel)
if accum_mode == "exact":
    w = len(sel) / size          # this micro-batch's SHARE of the group
elif accum_mode == "naive":
    w = 1.0 / accum_steps        # correct only while every micro-batch is equal
else:                            # none / unscaled
    w = 1.0
(loss * w).backward()
Green computing: compute is a finite resource The same data and the same accuracy are reachable with 9.07x fewer parameters, and this chapter measured it rather than asserting it. Parameters are a bill: 17,226 parameters reach 0.9785 and 1,898 reach 0.9808, and the extra 15,328 weights must be computed, moved and powered in training and at inference. "Reaching the goal with less" is not piety; it starts with one question — was this size necessary? Measure the peak memory before requesting compute, and report the optimisations that did not work: this week's augmentation cost 3 points of clean accuracy, and reporting only the 29-point robustness gain would be selective reporting.
Key terms
  • GPU memory — the memory held by activations, gradients and parameters during training; the thing batch size scales.
  • Out of memory (OOM) — the error raised when an allocation exceeds available memory; the most common lab blocker.
  • Gradient accumulation — summing gradients over several micro-batches before one optimiser step, to reach a larger effective batch without the memory.
  • Effective batch — micro-batch size times accumulation steps; the batch the update sees.
  • Mixed precision — using lower-precision arithmetic for most activations, with a loss scale to keep gradients usable.
  • Green computing — designing for the smallest compute that reaches the goal, and reporting the optimisations that did not pay off.

7.11 Summary and Exercises

Six takeaways
  1. A convolution is not a stronger layer; it trades a locality assumption for parameter efficiency. On the same data the parameter count differs by 9.07x and the accuracy by 0.0023 — smaller than one standard deviation, so "no significant difference was observed".
  2. Do the shape arithmetic before writing the code. The output-size formula (in + 2p - k)/s + 1 matches the real forward pass at every stage, and the receptive field follows 3 -> 4 -> 8 -> 10, with the second convolution already covering the whole 8x8 image.
  3. The pooling function is a choice, not a default. Max against average is worth 4.1 points at identical parameter count — several standard deviations.
  4. Augmentation buys robustness and pays clean accuracy: +29 points at dx = -1 for -3 points at dx = 0. Whether to buy is a question about whether your inputs are ever translated — a product question, not a model question.
  5. "98%" is not a result. A complete error analysis has four parts: the confusion matrix, the worst class pair with its count, concrete cases with probabilities, and a testable hypothesis. Here 26 errors remain, 12 involve the digit 8, and the worst pair is 8 -> 1 (three times).
  6. When you run out of memory, drop the batch first and buy the effective batch back with accumulation; with the share-of-group weighting it reproduces the true batch exactly (5/5). Report the optimisations that did not work.
