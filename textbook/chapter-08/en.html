Sequence Models and Text Data

Chapter 7 chose an architecture and counted what it cost. This chapter is about the plumbing underneath any text model, and about a bug that lives inside that plumbing and almost never announces itself. The task is small enough to hold in your head: given one English passage, decide which week of this course it came from (6 classes). The corpus is the course's own Weeks 1-6 materials, 748 passages, scrubbed of the week labels in 262 places so the task is not trivially solvable, with no download and no third-party licence. The spine of the week is not "the LSTM scores well" - it does not. The spine is that a single line deciding how a (B, T, 96) tensor becomes a (B, 96) vector moves the result from 0.2407 to 0.5027, a gap of 0.2620, while everything else stays identical. Along the way the chapter quantifies what masking buys (+11.0 points), shows why the worst arm's macro F1 (0.0711) sits below the 1/6 random baseline, and reaches the week's most honest conclusion: with only 523 training passages the binding constraint is data, so Week 6's regularisation, which helped there, lowers the score here from 0.5027 to 0.4672. Same tool, opposite answer, because the bottleneck changed.

8.1 From Text to Tensor: The Complete Pipeline

An nn.Embedding is a lookup table indexed by integer. A recurrent layer at step t consumes one integer and reads one row out of that table. Neither of them can hold a Python string, and neither of them has any notion of what a word is. That single fact is why every text task, however clever the model on top, begins with the same four-step conversion, and why an error in any of the four is invisible until the numbers come out wrong.

8.1.1 Why the Model Only Ever Sees Integers

Two layers define the contract. nn.Embedding(V, D) stores a matrix of shape (V, D) and, given a tensor of integer indices, returns the corresponding rows. nn.LSTM(input_size, hidden_size) accepts a tensor of shape (B, T, input_size) - floats - and steps over the T axis. So the integer is not a detail of the tokeniser; it is the index into a learned table, and the meaning of a word lives entirely in the row that training eventually writes there. Change the mapping from token to integer and you change which row learns which word. That is why the vocabulary must be built once and frozen before training begins, and why building it from the wrong data is not a cosmetic mistake.

8.1.2 The Four Steps, and the One Error Each Invites

Tokenisation (tokenisation)

Turn a string into a list of tokens. For English, lowercase and split on a regular expression; for Chinese, this is the step where a naive implementation silently destroys the input (Section 8.2). The typical error: splitting Chinese on whitespace, which yields one token per sentence and a vocabulary that never transfers.

Vocabulary (vocabulary)

Assign every token a stable integer id, reserving 0 for padding and 1 for the unknown token. The typical error: counting token frequencies over the whole corpus instead of the training set only - data leakage, and the reported OOV rate becomes a fiction (Section 8.3).

Encoding (encoding)

Replace each token with its id, mapping anything unseen to <unk>=1. The typical error: forgetting the unknown branch, so an out-of-vocabulary word crashes the batch - or, worse, letting an empty document produce an empty tensor.

Padding and masking (padding & masking)

Make every document in a batch the same length by appending <pad>=0, and carry the true lengths alongside so the model can ignore the padding. The typical error: reading the padding as if it were content. This is the bug the rest of the chapter is about (Sections 8.4 and 8.5).

8.1.3 Tokenisation and Vocabulary, in Code

The two functions below are the whole English half of the pipeline. They are written so that the single decision that matters - which documents the vocabulary is counted from - is a visible argument rather than a buried default.

import re
import torch

# A token starts with a letter and continues with letters, apostrophes or
# hyphens, so "don't" and "state-of-the-art" are each ONE token.
WORD = re.compile(r"[a-z][a-z'-]*")


def tokenise(text):
    """Lowercase, then keep only tokens that start with a letter."""
    return WORD.findall(text.lower())


def build_vocab(train_docs, min_freq=2, max_vocab=6000):
    """Count tokens over the TRAINING SET ONLY.

    Counting over the full corpus is data leakage: the test set's rare words
    would already be in the vocabulary, the OOV rate the report quotes would
    be understated, and the accuracy would be measured on a task easier than
    the one the model will face in production.
    """
    freq = {}
    for doc in train_docs:
        for t in tokenise(doc):
            freq[t] = freq.get(t, 0) + 1
    kept = [t for t, c in freq.items() if c >= min_freq]   # drop hapax-ish tokens
    kept.sort(key=lambda t: (-freq[t], t))          # frequent first, ties alphabetical
    kept = kept[:max_vocab - 2]                          # reserve ids 0 and 1
    return {t: i + 2 for i, t in enumerate(kept)}          # <pad>=0, <unk>=1


def encode(doc, vocab, max_len):
    ids = [vocab.get(t, 1) for t in tokenise(doc)]   # unseen token -> <unk>=1
    ids = ids[:max_len]                                 # truncate long documents
    return ids or [1]                                  # never return an empty list
Leakage is a one-word change, which is why it keeps happening Swap train_docs for all_docs and the code still runs, the model still trains, and the accuracy usually goes up. Nothing crashes and nothing warns. The vocabulary has simply been told about words it will not see until test time, so the OOV rate you measure is lower than the OOV rate you will get. This chapter returns to that trap with a measured number in Section 8.9, because the fix looks like a regression.

8.1.4 Padding and the Mask, in Code

Padding makes a batch rectangular; the lengths vector is what keeps the padding from being read as content. The masked mean is the reduction used by the best arm in this chapter, and its correctness is entirely in the two lines where the mask enters and where the divisor is chosen.

def pad_batch(docs, vocab, max_len):
    """Right-pad with <pad>=0. Returns (ids, lengths).

    `lengths` is not decoration. It is the only thing that lets the model tell
    a real token from a padded one, and it is what pack_padded_sequence needs.
    """
    enc = [encode(d, vocab, max_len) for d in docs]
    lengths = torch.tensor([len(e) for e in enc])
    T = int(lengths.max())            # this batch's width, not the global max_len
    x = torch.zeros(len(enc), T, dtype=torch.long)
    for i, e in enumerate(enc):
        x[i, :len(e)] = torch.tensor(e)
    return x, lengths


def masked_mean(out, x):
    """Average the real timesteps only.

    out: (B, T, H) hidden states   x: (B, T) ids, 0 where padded.
    The mask must be multiplied in BEFORE the sum, and the divisor must be the
    number of real steps, not T. Both halves matter; either one alone is wrong.
    """
    mask = (x != 0).unsqueeze(-1).float()                # (B, T, 1), 1 = real token
    return (out * mask).sum(1) / mask.sum(1).clamp(min=1)     # (B, H)

  • Token - the unit the model sees: a word-like string for English, a segment or a character for Chinese.
  • Vocabulary - the frozen map from token to integer id, with 0 reserved for padding and 1 for the unknown token.

8.2 Tokenisation: English, and the Chinese Trap

Tokenisation looks like the least interesting step and is the one that can be wrong by a factor of 39. The English recipe is uncontroversial; the Chinese recipe is where a student who has never segmented a language without spaces will produce a pipeline that appears to run and produces a vocabulary that transfers nothing.

8.2.1 English: Lowercase, Then One Regex

The rule used throughout this chapter is: lowercase the text, then extract every run that starts with a letter and continues with letters, apostrophes or hyphens. The pattern [a-z][a-z'-]* has three consequences worth stating plainly, because each is a choice.

  • Case is thrown away on purpose. LSTM and lstm become one token. The vocabulary shrinks and the model no longer has to learn two rows for one word - at the cost of losing the cue that a capitalised word often begins a sentence or names a thing.
  • Contractions and hyphenated words stay whole. don't is one token, not two; state-of-the-art is one token, not four. This is usually what you want for a small corpus, because splitting them multiplies the vocabulary with pieces that carry almost no signal on their own.
  • Numbers and punctuation disappear. A passage containing 17,226 contributes no token for it at all, because no run there starts with a letter. If a number is the signal you care about, this regex is the wrong tokeniser and you have to say so explicitly.

On this corpus the recipe is stable: the full 748-passage vocabulary is 3142 word types, and the median passage is 35 word tokens long (p25 26, p75 50, p95 87, max 285). Those two numbers - a modest vocabulary over short passages - are what make the task hard for the reason described in Section 8.10.

8.2.2 Chinese: Whitespace Tokenisation Is Simply Wrong

Chinese is written without spaces between words, so the English recipe has no equivalent. A tempting shortcut is to split on whitespace anyway. It is a shortcut that does not work, and here it is measured rather than asserted. Running both schemes on this repository's own Chinese textbook text (750 segments, split into 375 for the vocabulary and 375 for the test):

SchemeVocabularySingleton shareTest tokensOOV rate
Whitespace split (wrong)3720.99463750.9973
Character level (right)8800.217014,8600.0254

Read the two rows together and the failure is total. Under whitespace splitting the test set contributes only 375 tokens for 375 segments - one "word" per segment, because a segment of Chinese with no spaces is a single string. The out-of-vocabulary rate is 0.9973, which is not "high"; it means the whole passage is recognised as a single <unk>. The vocabulary is almost entirely singletons (0.9946) because no two segments happen to be identical, so nothing is shared and nothing is learned. Character level, by contrast, produces 14,860 test tokens from the same segments, an OOV rate of 0.0254, and a singleton share of 0.2170.

The OOV rate falls from 0.9973 to 0.0254 - a factor of 39. That is the size of the mistake, and it costs one line of code to avoid.

The engineering rule for a language without spaces Use a real segmenter first - jieba is the common one - which splits a sentence into word-like units. If no segmenter is available, fall back to character level, which is crude but correct: every segment becomes a sequence of characters, OOV is low, and the model can still learn from character patterns. What you must not do is fall back to whitespace, which is the one option that guarantees a vocabulary of length one per sentence. 
# Right: a segmenter, or character level as the fallback. Never whitespace.
def tokenise_zh(s, use_jieba=True):
    if use_jieba:
        try:
            import jieba
            return [t for t in jieba.lcut(s) if t.strip()]
        except ImportError:
            pass
    return list(s)          # character level: crude, but OOV = 0.0254, not 0.9973
    # return s.split()    # <- the bug: one token per sentence, OOV = 0.9973
Key terms
  • Tokenisation - splitting a string into the units the vocabulary will hold.
  • Word segmentation - recovering word boundaries in a language that does not mark them with spaces; the step Chinese needs and English does not.
  • Character-level tokenisation - taking one token per character; a correct fallback when no segmenter is available.
  • Out-of-vocabulary (OOV) rate - the fraction of test tokens that are not in the training vocabulary; here 0.9973 versus 0.0254.
  • Singleton - a token that occurs exactly once in the training vocabulary; a high singleton share means the vocabulary is not reusable.

8.3 Vocabulary and Encoding

The vocabulary is a contract between the tokeniser and the embedding table, and it is frozen before training. Three parameters define it in this chapter, and each is chosen for a reason that can be defended.

8.3.1 Three Settings and Why They Are Set That Way

SettingValueReason
Minimum frequencymin_freq = 2A token seen once in training cannot be learned; it becomes a row that is barely updated. Dropping it keeps <unk> meaningful and shrinks the table.
Vocabulary cap6000An upper bound on the embedding table. This corpus never reaches it, but the cap bounds parameter growth and memory if the corpus grows.
Reserved ids<pad>=0, <unk>=1Padding needs a fixed id so that the mask x != 0 works; the unknown token needs a fixed id so encoding never fails.

The vocabulary is counted over the training documents only, and the count is produced at the same time the ids are assigned, so frequencies and ids cannot drift apart. For seed 42 the result is a vocabulary of 1617 entries; averaged over the five seeds the model sees 1592. The full corpus, if you counted every passage, holds 3142 word types - and that second number is the one the model must not have been given.

8.3.2 Counted From the Training Set Only

Two vocabularies, two stories. The honest one counts tokens over the 523 training passages and nothing else, so a token the model meets for the first time at test is genuinely unknown and genuinely maps to <unk>. The leaky one counts over all 748 passages, which means the test set's rare words already sit in the table with an id, and the model is graded on a task that has been quietly made easier.

Why this is the most common leakage in text modelling Splitting the arrays is easy to remember; splitting the preprocessing is not. The tokens are already sitting in a list, and counting them is a two-line loop that does not obviously belong to either side of the split. The discipline is the same as Chapter 3's and Chapter 6's: anything that is fit - a scaler, an imputer, a vocabulary - is fit on the training split, and the test split is only ever transformed, never fit on. A vocabulary is fit. Section 8.9 measures what happens when you forget.

8.3.3 padding_idx=0 and the Gradient That Never Arrives

Passing padding_idx=0 to nn.Embedding does more than document which row is padding. At every backward pass, PyTorch zeroes the gradient contribution of that row, so the embedding vector for <pad> never receives an update. It starts as zeros and stays zeros. This matters because pooling that ignores the mask will still multiply real hidden states by a zero vector; the row not moving does not save you, but it does mean the padding row carries no learned signal to mislead the optimiser elsewhere.

emb = nn.Embedding(1617, 64, padding_idx=0)

ids = torch.tensor([[5, 6, 7, 0, 0]])
out = emb(ids)                       # (1, 5, 64); rows 3 and 4 come from row 0
out.sum().backward()                  # a non-trivial loss, to force a gradient
print(emb.weight.grad[0].abs().sum())     # tensor(0.) - the pad row never learns
Key terms
  • Vocabulary size - the number of distinct ids, including the two reserved ones; 1617 for seed 42, 1592 on average.
  • <pad> / <unk> - the two reserved ids: 0 for padding and 1 for everything out of vocabulary.
  • padding_idx - tells the embedding layer which row is padding, so its gradient is forced to zero on every step.
  • Frozen vocabulary - built once from the training split and never updated during training or evaluation.

8.4 Padding and Masking

An LSTM steps over a fixed T axis, but documents come in different lengths. Padding is the reconciliation - and the mask is what stops the reconciliation from corrupting the answer. This section is the core of the chapter, because every failure later in the chapter is a masking failure wearing a different hat.

8.4.1 Variable Length to Fixed Length

In a batch of 64 documents, the array has to be rectangular: shape (64, T). T is either the longest document in that batch or the global cap max_len = 96, whichever is smaller. Every shorter document is filled with <pad>=0 on the right. The lengths vector records the true length of each row, and it is the only place that information survives.

The scale of the padding is not small. On the seed-42 test set, 95.58% of the documents are shorter than max_len = 96. In other words, almost every document in almost every batch has a tail of padding, and any code that reads the tail is reading padding on almost every example. That single percentage is why the bug in Section 8.5 does as much damage as it does.

8.4.2 The Mask, and the Correct Masked Mean

A mask is a tensor that is 1 wherever a position is a real token and 0 wherever it is padding. Built from the ids themselves, (x != 0) is already exactly that - no extra bookkeeping is needed, because <pad> is id 0. The mask is then shaped to broadcast against the hidden states and applied before the reduction.

out, _ = rnn(emb(x))                    # out: (B, T, H)

mask = (x != 0).unsqueeze(-1).float()     # (B, T, 1) -> broadcasts over H

# correct: sum the real positions, divide by the number of real positions
z = (out * mask).sum(1) / mask.sum(1).clamp(min=1)      # (B, H)

# the quiet bug: divide by T, so every padded position drags the mean toward 0
z_wrong = out.mean(1)                      # (B, H) - averages the padding too

Both lines run, both return the right shape, and neither raises a warning. The difference is the divisor and the mask, and their effect is measured in Section 8.8: the correct masked mean 0.5027, the unmasked mean 0.3929, a gap of 0.1098 - about 11.0 points - from a single missing multiply.

The mask has to enter before the sum, and the divisor has to match Two ways to get this wrong, and they are not the same mistake. If you mask after the mean (out.mean(1) * something) the padded rows have already contributed. If you mask the sum but still divide by T, every short document is scaled down by its fraction of real tokens, so a 35-token document is divided by 96 and its vector is quietly shrunk to about a third. The mask must go into the sum, and the divisor must be the mask's own count.
Key terms
  • Padding - appending <pad> so a batch is rectangular; 95.58% of test documents are shorter than the cap.
  • Mask - a 0/1 tensor marking real positions; here (x != 0), needing no separate bookkeeping.
  • Masked mean - summing only the real positions and dividing by their count, (h * mask).sum(1) / mask.sum(1).
  • Variable-length sequence - a document whose true length differs from the batch width; the situation padding exists to resolve.

8.5 Anatomy of the out[:, -1, :] Bug

This is the bug the week is built around, and it deserves a full dissection because it has every property of a bug that ships: it is one line, it is idiomatic, it runs without error, its output has the correct shape, and its damage is concentrated in exactly the samples nobody inspects.

8.5.1 The Wrong Line and the Right Line

After the LSTM, out has shape (B, T, H). The intent is "the model's reading of the document" - one vector of length H per example. The wrong line takes the last column:

# ---- WRONG: out[:, -1, :] -------------------------------------------------
# Column T-1 is the state after the LSTM consumed the LAST POSITION. For a
# document shorter than the batch width, those positions are <pad>=0. So the
# vector read here is the hidden state after reading the padding - not the
# document. 95.58% of the test documents are shorter than max_len = 96, so
# almost every example is read to the wrong place.
out, _ = rnn(emb(x))
z_bad = out[:, -1, :]                     # (B, H) - the last COLUMN

# ---- RIGHT: pack, then take the last REAL hidden state --------------------
# pack_padded_sequence drops every padded timestep, so the LSTM stops at each
# document's true length. It needs the batch sorted by length descending, OR
# enforce_sorted=False, which sorts internally and restores the original order
# on the way out. h[-1] is then the last hidden state of the top layer, per
# sample, at each sample's own final real token.
packed = nn.utils.rnn.pack_padded_sequence(
    emb(x), lengths, batch_first=True, enforce_sorted=False)
_, (h, _) = rnn(packed)
z_ok = h[-1]                                # (B, H) - the last REAL token

Only one document in a batch is read correctly by the wrong line: the longest one, whose final position happens to be a real token. Every other document is read at a position that only exists because of padding. The shorter the document, the more padding stands between its true end and the position the model actually reads.

import torch, torch.nn as nn

torch.manual_seed(0)
B, T, H, V = 4, 8, 96, 100
emb = nn.Embedding(V, H, padding_idx=0)
rnn = nn.LSTM(H, H, batch_first=True)

x = torch.tensor([[5, 6, 7, 0, 0, 0, 0, 0],     # length 3
                  [8, 9, 1, 2, 3, 4, 5, 0],     # length 7
                  [1, 2, 3, 0, 0, 0, 0, 0],     # length 3
                  [7, 8, 9, 10, 11, 12, 13, 14]])  # length 8 (full)
lengths = (x != 0).sum(1)                        # tensor([3, 7, 3, 8])

e = emb(x)
out, _ = rnn(e)

z_bad = out[:, -1, :]                              # reads the padding
packed = nn.utils.rnn.pack_padded_sequence(
    e, lengths, batch_first=True, enforce_sorted=False)
_, (h, _) = rnn(packed)
z_ok = h[-1]                                    # reads the last real token

print(torch.allclose(z_bad[3], z_ok[3]))              # True  - row 3 is full length
print(torch.allclose(z_bad[0], z_ok[0]))              # False - row 0 is padded

8.5.2 Three Kinds of Evidence That the Diagnosis Is Right

It is not enough to say "the wrong line reads padding"; a diagnosis has to predict something about the numbers, and the predictions have to hold. Three measurements do so, and each rules out a competing explanation.

Evidence 1 - the damage lands on short documents. If the bug is "reads the padding", it should hurt a 20-token document more than a 100-token one, because the shorter the document the more padding sits between it and the last column. Bucketing the seed-42 test set by true length shows exactly that, and shows it only for the wrong line:

The correct arm is flat across buckets - between 0.39 and 0.60, roughly the class prior. The wrong arm is not: it collapses to 0.1579 and 0.1707 on the short buckets and only recovers to 0.4138 once documents are long enough that padding is a small fraction of the row. The damage tracks padding, which is what the diagnosis predicts.

Evidence 2 - the hard boundary at max_len. The prediction sharpens at the cap. A document at or above max_len = 96 has no padding at all, so out[:, -1, :] really does point at its end. A document below the cap does not. On the seed-42 test set:

  • Documents of length at least 96: 5 of them, wrong-arm accuracy 0.4000.
  • Documents of length below 96: 108 of them, wrong-arm accuracy 0.2315.

The five full-length documents are read correctly and score like the correct arm; the 108 padded ones collapse. This is the evidence that rules out the tempting alternative explanation - "the task is just too hard" - because if the task were the problem, the long documents would not do better.

Evidence 3 - changing max_len does not save the wrong arm. If the bug is about where padding sits, then padding less or more should move the wrong arm, and it should barely touch the correct one. Sweeping the cap over three seeds (42, 43, 44):

The correct arm moves by 0.0118 across the whole sweep, which is well inside its own standard deviation, so tuning the cap is not a lever. The wrong arm moves around without ever catching up. The lesson is the one the whole section is for: if the pooling is wrong, no length setting fixes it.

The mechanism in one sentence, and the general shape of the mistake out[:, -1, :] assumes the last position in the padded tensor is the last position of the document; pack_padded_sequence plus h[-1] (or a masked mean) uses the true lengths and stops where the document stops. The general shape of the mistake is a fixed reduction over a variable-length axis: whenever a tensor has a padded axis, any operation that treats every position as real - a last-position lookup, an unmasked mean, an unmasked max - is wrong, and the only question is how much it costs.
Key terms
  • pack_padded_sequence - a PyTorch helper that drops padded timesteps so the recurrent layer stops at each document's true length.
  • enforce_sorted - when False, the pack sorts the batch by length internally and restores the original order; when True you must pre-sort.
  • Last real hidden state - the state after the final non-padded token; the correct target of a last-step read.
  • Pooling - the reduction that turns the sequence of hidden states into one vector per document.
  • Fixed reduction over a variable axis - the pattern of bug; reads padding as content, runs without error, and hides in short samples.

8.6 RNNs and Vanishing Gradients

The recurrent layer inherits the problem that every deep network has, but in a form that is worse and more specific. The recurrence is where the sequence model's reach comes from, and it is also where its gradients go to die.

8.6.1 The Recurrence

A plain recurrent layer keeps a hidden state of length H and updates it once per token:

ht = tanh(W xt + U ht-1 + b)

where xt is the embedding of the token at step t and W, U, b are shared across every step. The sharing is not an optimisation; it is the definition. It is what lets the same layer accept a 20-token document and a 285-token one, and it is what makes the whole thing trainable with one set of parameters.

import torch

H, T = 96, 5
W = torch.randn(H, H) * 0.1
U = torch.randn(H, H) * 0.1
b = torch.zeros(H)

h = torch.zeros(H)                          # initial state
xs = torch.randn(T, H)                      # one embedding per step
for t in range(T):
    h = torch.tanh(xs[t] @ W.T + h @ U.T + b)   # the recurrence, written out

Training a recurrent network is ordinary backpropagation through time: the loss at the last step is differentiated with respect to every earlier step, so the gradient reaching step k is a product of one Jacobian per intervening step. That product is where the trouble is.

8.6.2 Why the Gradient Disappears, or Explodes

Differentiate the recurrence and the transition factor appears:

dht / dht-1 = diag(1 - tanh2(...)) U

So the gradient at a step k steps in the past is multiplied by a chain of these factors - about T of them. Two things happen to that chain.

  • Vanishing. The derivative of tanh is at most 1 and typically well below it, and the entries of U are small after initialisation. A product of many numbers each below 1 shrinks exponentially: by the time the gradient travels back across 50 steps it is a number so small it is indistinguishable from zero, and the parameters that shape the early part of the sequence stop learning.
  • Exploding. If the entries of U happen to be large, the product grows instead, and the gradient overflows. The usual symptom is a loss that jumps to nan; the usual fix is gradient clipping, which caps the norm of the gradient before the optimiser step.

On this corpus the problem is present but not the binding one: the median document is 35 tokens and the cap is 96, which is short enough that a vanished gradient is a nuisance rather than the reason the score is low. The reason the score is low is the thing Section 8.9 measures - too little data - and it is worth keeping the two apart, because they call for different fixes.

Key terms
  • Hidden state - the vector the recurrent layer carries across steps; length H.
  • Shared weights - one W and one U used at every timestep, which is what makes a variable-length input possible.
  • Backpropagation through time (BPTT) - backpropagation applied across the unrolled recurrence.
  • Vanishing gradient - the gradient's exponential decay across many steps, so early steps stop learning.
  • Exploding gradient - the opposite; a gradient that overflows, usually cured by clipping its norm.

8.7 LSTM and GRU: Gating, and What It Does Not Fix

The long short-term memory cell was invented to give the gradient a path that does not have to survive a chain of tanh derivatives. It does this with gates, and the gates are easiest to understand one at a time as answers to a specific question.

8.7.1 Three Gates, Three Questions

GateThe question it answersWhat it controls
Forget gate ftHow much of the old memory should survive?Scales the previous cell state Ct-1; a value near 0 erases, near 1 keeps.
Input gate itHow much of the new candidate should be written in?Scales the candidate update; decides what is worth remembering from this token.
Output gate otHow much of the memory should be exposed right now?Scales the cell state on its way to the hidden state ht.

The mechanism that matters for gradients is the cell state Ct, updated as Ct = ft * Ct-1 + it * candidate. Along the cell-state path the transition is a multiplication by the forget gate rather than by a weight matrix times a tanh derivative. When the forget gate sits near 1, that path is close to an identity, and gradients can flow across many steps without shrinking as fast. This is what "LSTM solves vanishing gradients" actually means - not that the problem is gone, but that there is now a route on which it is much milder.

8.7.2 The Cost: It Is Still Sequential

Gating buys a better gradient path and costs nothing in correctness, but it does not change one structural fact: the recurrence is still a loop. Step t needs ht-1, so the T steps of a document cannot be computed in parallel no matter how many cores are available. A GRU is a cheaper variant of the same idea - it merges the forget and input gates into one update gate and drops the separate cell state, with two gates instead of three - and it is sequential in exactly the same way.

The bridge to Module 3 That sequential dependency is the reason the field moved on. The attention mechanism, and the Transformer built from it, computes every position's representation from every other position at once, with no recurrence at all - so the whole sequence is parallel and the vanishing-gradient problem along a chain disappears. Chapter 10 takes that up directly, and it will use this week's LSTM as the contrast: same task, same data, a different answer to "how does a position see the others?" Keep this chapter's numbers, because they are the baseline the Transformer has to beat.
Key terms
  • Gate - a sigmoid layer whose output, between 0 and 1, scales a signal; gates are how a cell decides what to keep.
  • Forget gate - scales the previous cell state; near 0 forgets, near 1 keeps.
  • Input gate - scales the new candidate written into the cell state.
  • Output gate - scales the cell state on its way out to the hidden state.
  • Cell state - the LSTM's long-term memory path; because its transition is a multiplication by the forget gate, it gives the gradient an easier route.
  • GRU - a two-gate simplification of the LSTM; cheaper, and sequential in the same way.

8.8.2 The Honest Baseline: The Worst Arm Is Below Chance

With 6 balanced-ish classes, random guessing reaches 1/6 ≈ 0.1667 on accuracy. That is the number every arm has to beat before it is doing anything at all. last_step reaches 0.2407 on accuracy, which clears 0.1667 - but its macro F1 is 0.0711, which is below the random baseline. The reason is simple once the confusion matrix of Section 8.10 is in front of you: the wrong arm predicts the largest class almost always, so it collects accuracy from prior alone and finds almost no examples of the small classes. Macro F1, which weights every class equally, sees through it.

0.5027 is a real result, not a good one It is three times the random baseline, and the sample of 113 test documents per seed is small enough that the ±0.0449 spread matters. No sentence in this chapter should read as "the LSTM classifies text well". The correct sentence is: on this corpus, with this much data, the best configuration reaches 0.5027, and the size of the gap between configurations dwarfs the absolute level of any of them. The chapter is about the gap, because the gap is what you control.
Key terms
  • Arm - one configuration under test, with every other factor held fixed.
  • Pooling - the reduction from a sequence of hidden states to one vector; here the only variable that changes.
  • Random baseline - the score of guessing; 1/6 ≈ 0.1667 with 6 classes.
  • Macro F1 - the unweighted mean of per-class F1; the metric that exposes an arm relying on the class prior.
  • Seed replication - repeating an arm over several seeds so the spread, not one run, is the measurement.

8.9 Overfitting, Regularisation, and the Wrong Bottleneck

Every arm overfits. The interesting question is not whether it does - with 523 training passages and a model that reaches 0.9885 on them, it does - but what kind of overfitting it is, and therefore what would fix it. This section answers that question with two measurements and reaches the week's most important honest conclusion.

8.9.1 The Training Curve, for One Seed

For packed at seed 42, recorded every 3 epochs for 11 points, training accuracy climbs from 0.2849 to 0.9885 while validation accuracy climbs from 0.2143 to 0.4196. At epoch 30 the gap is 0.9885 - 0.4196 = 0.5689. The model has memorised the training set and its validation score has stalled at roughly the level of its test score.

Look at the validation column and note what it does not do: it never declines. There is no peak and no downward turn - the curve is still creeping upward at the last recorded point. That shapes the diagnosis. If the problem were simply "trained too long", the validation curve would have turned down and early stopping would be the answer. A validation curve that has never fallen is not the signature of training past the optimum; it is the signature of a model that has learned everything the data can teach and is now filling the rest of its capacity with noise.

8.9.2 Applying Week 6's Regularisation Makes It Worse

Chapter 6 taught two regularisers that worked there: dropout on the hidden representation and weight decay on the optimiser. Applying both to the best arm - mean_masked with dropout 0.3 and weight decay 1e-3 - is a controlled test of the bottleneck hypothesis:

ArmTest accuracyMacro F1
mean_masked0.5027 ± 0.04490.4774 ± 0.0482

The score falls from 0.5027 to 0.4672 - a drop of 0.0355, about 3.6 percentage points - and macro F1 falls by 0.0341, about 3.4 points. Worse than the fall is the change in spread: the standard deviation across seeds grows from ±0.0449 to ±0.0595, so the regularised arm is both lower and less stable. On this task, the two tools that help a model with plenty of data and too much capacity do the opposite: they remove capacity the model still needed.

The conclusion, stated plainly The binding constraint this week is the data, not the capacity. There are 523 training passages. The train-validation gap of 0.5689 looks like overfitting, but it is overfitting on a model whose capacity is not the limiting factor - so constraining that capacity (dropout, weight decay) only removes the little signal the model had. The lever that would move this number is more passages, or a different task definition; regularisation is not the lever here.
The same tool, two opposite answers In Week 6 the same two regularisers raised the score: there the data was plentiful and the model was large, so capacity was the bottleneck and constraining it helped. Here the data is scarce and capacity is not the bottleneck, so the identical tool hurts. This is not a contradiction in the tools; it is a reminder that a technique is not a rule, it is a response to a diagnosed bottleneck. The procedure is always the same: measure which constraint is binding first, then choose the tool. Applying the tool that worked last time, without the measurement, is how a working model gets worse while the engineer believes they improved it.

8.9.3 The False Improvement of Building the Vocabulary on Everything

The other tempting "fix" is to widen the vocabulary by counting tokens over all 748 passages instead of the 523 training ones. It raises the vocabulary from 1592 (the five-seed mean) toward the full-corpus count of 3142, and it usually raises the score. It is also leakage, and the rise is a lie: the vocabulary now contains the test set's rare words, so the OOV rate the report measures is lower than the OOV rate the model will meet on genuinely new text. The measured rise is because the task has been made easier, and no honest report can quote it as an improvement. Exercise 2 makes you run it and see the shape of the false gain for yourself.

Key terms
  • Overfitting - a model that fits the training set much better than unseen data; here the train-validation gap is 0.5689.
  • Dropout - randomly zeroing hidden units during training to reduce effective capacity.
  • Weight decay - an L2 penalty on the weights, shrinking them toward zero.
  • Binding constraint - the factor that actually limits the score; here the 523 training passages, not the model's size.
  • False improvement - a gain that comes from leaking test information rather than from a better model.

8.10 Error Analysis and the Choice of Metric

An accuracy number is a sentence with the important part left out. This section opens the confusion matrix, reads the recall column per class, and shows the one signal that decides whether a model ships or does not: the split between accuracy and macro F1.

The off-diagonal is almost flat. Every off-diagonal cell sits between 4 and 22. There is no pair of weeks the model confuses more than any other - no 8-and-1 of this task. The only cell on the diagonal that stands out is W6 at 93, and that is not the model being good at Week 6; it is Week 6 being the largest class (140 test examples against Week 1's 80).

Recall rises with class size (Spearman rho = 0.77). Recall is 0.1750 for W1, 0.1867 for W2, 0.4235 for W3, 0.4778 for W4, 0.4211 for W5 and 0.6643 for W6. There are two small inversions — W2 above W1, and W5 against W4 — in an otherwise rising sequence, and the trend is unmistakable: the bigger the class, the better the model finds it. W6's recall is 3.80 times W1's. A model that finds big classes well and small classes badly is not learning the content - it is learning the prior, and predicting the common week more often. This is the direct evidence behind the flat off-diagonal: with no pair of weeks more separable than the others, predicting by frequency is as good a strategy as the model has found.

8.10.2 Accuracy and Macro F1 Split: The Signal That Stops a Bad Model Shipping

For the last_step arm the two metrics disagree by a wide margin:

ArmTest accuracyMacro F1Random baseline
last_step0.2407 ± 0.00400.0711 ± 0.00951/6 ≈ 0.1667

Accuracy is 0.2407; macro F1 is 0.0711. The gap is 0.1696 - about 17 points - and the direction matters: accuracy sits above the random baseline while macro F1 sits below it. A report that quoted only accuracy would describe a model that looks better than a coin flip, and would send it to production. Macro F1, which scores every class equally, exposes a model that has learned to say the largest class and almost nothing else. The metric is not a formality; it is the difference between a working model and a confident one.

The metric follows from the cost of being wrong When classes are imbalanced and the cost of a missed small class is as high as a missed large one, accuracy is the wrong instrument and macro F1 is the right one. When the cost is genuinely proportional to class size, accuracy is defensible. The choice is a statement about what a mistake costs - which is why it belongs to the people who own the consequence, not to a default. This is the week's civic point: choosing a metric is choosing whose errors you are willing to accept.

8.10.3 The Fourteen Misses, Read as Text

The packed arm at seed 42 misses 14 of the 113 test passages. Read as text rather than as cells, they fall into three kinds, and none of them is the model failing.

Short sentences, where the vocabulary has the least to work with (20 tokens) - true W4, predicted W3

"Hidden layers transform the features first; the output layer decides afterwards. The same data becomes separable in the new space." At 20 tokens this is the minimum length the corpus admits, and it names generic concepts with few tokens to anchor them to a week.

General engineering sentences, true of every week (26 tokens) - true W1, predicted W2

"Hyper-parameters, data paths, batch size and split ratios live in a file or a single dictionary - not scattered through the code and not in your memory." This sentence is good advice in Week 1 and in Week 6; it carries no week-specific vocabulary at all, so no classifier could place it by content.

Terminology reused across weeks (22 tokens) - true W6, predicted W4

"Explain how a training set of 80 samples against 17,226 parameters produces overfitting on purpose, and why that is the point of the lab." The passage contains 17,226, a number that appears in the Week 4 material as well; the model has the vocabulary but the vocabulary does not belong to one week.

None of these is the model looking at the wrong thing In all three cases the model's prediction is defensible from the words in the passage: the sentences genuinely belong to more than one week. "Which week is this passage from" has no unique answer for a passage that reuses another week's vocabulary - the label is a property of where the passage was filed, not of what it says. That is not a failure to be fixed with a bigger model; it is the boundary of the task definition. The honest response is to name it in the report, and to consider whether the task should be redefined (predict the topic, accept multiple labels) rather than whether the model should be retrained.
Key terms
  • Confusion matrix - rows true class, columns predicted; the diagonal counts correct decisions and each off-diagonal cell is a specific confusion.
  • Recall - of a class's true examples, the fraction found; here from 0.1750 for W1 to 0.6643 for W6.
  • Class prior - the base rate of a class; a model that predicts the largest class exploits it.
  • Accuracy / macro F1 split - accuracy above the baseline while macro F1 is below it; the signal that a model only predicts the prior.
  • Error analysis - reading the misclassified samples as text to find what the aggregate number hid.

8.11 Summary and Exercises

Six takeaways
  1. A text model never sees a string. Four steps turn text into a tensor - tokenise, build the vocabulary, encode, pad and mask - and the vocabulary is built from the training split only. Anything else is leakage, and Section 8.9 shows why the resulting gain is a lie.
  2. Tokenisation is not cosmetic. On Chinese text, splitting on whitespace gives an OOV rate of 0.9973 - one token per sentence, so each passage is one <unk> - against 0.0254 at character level, a factor of 39. Segment first, fall back to characters, never to whitespace.
  3. Padding is the majority of the tensor: 95.58% of test documents are shorter than max_len = 96. The mask must enter the sum before the reduction and the divisor must be the mask's own count; the masked mean is worth about 11.0 points over the unmasked one.
  4. out[:, -1, :] reads padding on every short document. Its signature is that the damage tracks document length - 0.1579 on 20-29 tokens, 0.2315 below max_len versus 0.4000 at or above it - while the correct arm is flat. Fixing the reduction moves the score by 26.2 points, and no max_len setting substitutes for it.
  5. Regularisation is a response to a bottleneck, not a rule. This week the bottleneck is 523 training passages: dropout and weight decay take the score from 0.5027 to 0.4672, and widen the spread from ±0.0449 to ±0.0595. In Week 6 the same tools helped, because there the bottleneck was capacity. Diagnose first.
  6. Report the metric that matches the cost of a mistake. The last_step arm shows accuracy 0.2407 against macro F1 0.0711 - above chance on one, below it on the other. And the fourteen misses are not model errors: the passages belong to more than one week, so the task itself has no unique answer for them.
