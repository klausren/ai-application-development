第 01 章 · 模块 1 · 第 1 周

AI 应用开发导论与岗位认知

AI 应用开发不是「训练一个模型」，而是「把一个模型变成别人能用的系统」。本章为整个学期建立地图：端到端流水线长什么样、产业实际招的是哪几类角色与哪些能力、你的工作台由哪些工具组成，以及在报出任何一个数之前，「可复现」必须具备什么含义。本章也会明确说明：本课程在什么位置欢迎 AI 协助，在什么位置不允许。

1.1 AI 应用开发到底是什么

几乎所有刚开始学这门课的人都有同一个想象：坐下来训练一个模型，这个模型就是「产品」。这个想象错得很具体，也很贵。一个训练好的模型，如果没有数据管道、没有评估协议、没有接口、没有监控，那它是一件研究制品，不是应用——它回答不了任何人的问题。

1.1.1 传统软件 vs AI 应用

区别不在于「AI 更聪明」，而在于规则被搬走了。

传统软件AI 应用
行为从哪来人写的规则从数据里学出来的模式
输出的性质确定性、可预测带概率性；是一个分布，不是一个值
怎么验证断言：输出等于预期统计度量：精度、F1、时延、成本
难点在哪逻辑复杂度数据质量、泛化、工程化
谁为失败负责写规则的人搭流水线的人——包括「没泛化好」这件事
一句话记住 传统软件说「规则我告诉你」，AI 应用说「例子我给你，规则你自己总结」。一旦你选了后者，你就同时接手了「规则总结错了」的责任。

垃圾邮件过滤是最好的例子。手写规则（「含 free」「发件人陌生」）能撑到某位叫 Cash 的客户来信谈合同为止。那一刻你就停止写规则、开始收集样例——同时接手了一类新问题：这个系统会以没有人写下来的方式出错。

1.1.2 六步流水线

从学生作业到生产系统，每个 AI 应用都走同样六步。跳过任何一步都不省时间，只是把成本挪到更晚、更贵的地方。

问题定义

目标用户是谁、要解决什么问题、什么算成功、什么算失败。失败判据必须在建模之前写下来——因为你一旦看到结果，就会为任何结果找理由。

数据

获取、清洗、划分、标注，并核对许可。数据决定上限；没有任何建模技巧能把这个上限抬高。

建模

先基线，再简单模型，最后才是更强的模型。基线不是可选项——没有它，「我们的模型到了 0.87」是一个没有含义的数。

评估

离线指标、错误分析，以及指标与业务真实代价之间的对齐。没人在意的指标只是装饰。

部署

封装接口、测时延与吞吐、处理畸形输入时返回干净的错误而不是一串 traceback。

运维

监控、版本、漂移检测与再训练。生产上最常见的故障不是「模型差」，而是「模型还行，但喂进来的数据变了」。

本周的坑 模型只是六步里的第 3、4 步。把 90% 精力花在第 3 步的人，到第 16 周往往交不出能演示的东西——因为它既没有数据故事，也没有办法被跑起来。

1.2 AI 应用技术栈

1.2.1 四层与两条贯穿线

出问题时，第一个有用的问题是「这属于哪一层」。答案决定了该谁修、以及要修多久。

应用层

界面、API、业务流程。决定「有没有人真的用它」。一个技术上完全正确的模型，如果输出没法被使用，在这里变成废物。

模型层

训练、微调、推理、评估。本课程的主战场（W4–W12）。也是学生最容易过度投入、却最容易被替换的一层。

数据层

采集、存储、清洗、版本。决定上限。这一层的泄漏 bug 会产出一个漂亮但毫无意义的分数（见第 3 章）。

基础设施层

算力（GPU）、容器、调度。决定成本与速度。性能高 2%、成本高 40 倍，那是一个决策，不是一次胜利。

贯穿 · MLOps

实验管理、版本、监控与数据测试。没有它，「现在线上是哪个模型」没有人答得出来。第 14 周专讲。

贯穿 · 负责任 AI

公平、可解释、安全与隐私。它不是最后补上的检查表，而是对其它每一层的约束条件。第 15 周专讲。

1.2.2 产业生态

不同领域的术语差别极大，但在「怎么衡量」上高度一致。无论什么应用，你报的都是同样两类数字。

领域典型任务质量指标工程指标课程对应
计算机视觉图像分类、缺陷检测、分割mAP、精度、漏检率帧率、显存占用W7、W9
自然语言处理文本分类、序列标注、情感分析F1、精度、忠实度每秒 token 数、千次调用成本W8、W10
大模型应用信息抽取、问答、检索增强生成解析成功率、命中率、答案可溯源性单次时延、单次 token 消耗W11、W12
工程与运维推理服务、监控、版本管理错误率、漂移告警P50/P95 时延、吞吐、可用性W13、W14
一句话 质量回答「预测得对不对」，工程回答「跑得多快、多贵」。只报其中一类的，是半个结果。

1.3 AI 工程师：角色、能力与工作流

1.3.1 三类核心角色

数据工程

把原始数据变成可训练的数据集：清洗、划分、泄漏识别、Dataset/DataLoader。对应第 3 周与实验 2。

模型工程

选择、搭建、训练与评估模型：结构、损失函数、训练循环、超参数搜索。对应第 4–10 周。

应用与部署工程

把模型封装成稳定可用的东西：接口、时延预算、错误契约、监控与版本。对应第 13–14 周。

在大公司这三件事是三个不同的人；在本课程（以及大多数小公司里）它们是你，在一周里的三天。

1.3.2 岗位能力矩阵

注意这张表里没有什么：没有任何一行写成「会某某算法」。每一行都用「你能交付什么」来定义，因为要求实际就是这样被检验的——被面试官、被评分者、被用户。

1.3.3 一位 AI 工程师的一周

下面这个循环会一直重复。其中有两步是本课程评分表里的硬规则。

对齐需求

和真正为结果负责的人确认问题、指标与失败判据。写下来。

摸数据

看分布、缺失、不平衡与泄漏。这一步杀死的项目比建模多得多。

打基线

规则一。用最笨但可能有效的方法拿到一个数——多数类、随机、或一条经验规则。没有基线，改进就没有含义。

一次只改一个变量地迭代

规则二。改一处、记录对照，再改下一处。一次改三处会得到一个更好的数，和零知识。

交付并监控

封装、写文档、持续观察。一个输入悄悄漂移、却没人知道的模型，比没有模型更糟——因为大家已经开始信它了。

1.4 开发环境与工具链

1.4.1 为什么先做隔离

环境问题是机器学习课上被最严重低估的成本。一次「跑不起来」就能吃掉一个十五周项目里的一整周。隔离是能买到的最便宜的保险：一个项目一个环境，为某个任务装的依赖坏了另一个任务的可能性就消失了。

# 建立隔离环境并激活
conda create -n ai-app python=3.11 -y
conda activate ai-app

# PyTorch，CPU 版（任何机器都能跑）
conda install pytorch torchvision -c pytorch -y

# 导出环境快照，换机器可重建
conda env export --no-builds > environment.yml
高频故障 ModuleNotFoundError 几乎总是说明跑的是错误的解释器或 kernel，而不是包没装。先确认 which python 与当前激活的环境，再考虑重装。仅这一个习惯就能解决第一周大部分求助。

1.4.2 工具链五件套

组件作用本课程的要求
Python + conda语言与环境隔离每个项目的 environment.yml 都要入库
PyTorch框架——本学期唯一使用CPU 与 GPU 都能跑；每次都要报出设备
GPU / CUDA加速器检查 torch.cuda.is_available() 并记录结果；只用 CPU 也可接受
Notebook / IDE工作台Notebook 用于探索；可复用代码落成 .py 模块
Git版本控制，以及你工作的「时间戳」每周至少一次有意义的提交；提交时间即提交截止时间

1.4.3 环境自检

三行就足以证明一个环境可用。把输出存下来——它是实验 0 的第一份证据。

import sys, torch

print("python :", sys.version.split()[0])
print("torch  :", torch.__version__)
print("device :", "cuda" if torch.cuda.is_available() else "cpu")

# 如果有 GPU，把型号与显存也记下来
if torch.cuda.is_available():
    print("gpu    :", torch.cuda.get_device_name(0))
    print("vram   :", round(
        torch.cuda.get_device_properties(0).total_memory / 1e9, 2), "GB")

要证明的是三件事：版本就是你装的那个、设备能被识别、显存看得见。「能 import」不在其中。

1.5 可复现性：种子、配置、版本

「我这里能跑」说的是你的机器。标准要高得多：换台机器、换个时间、换个人来跑，结果一样。

1.5.1 三要素

① 随机种子

把每一处随机源都固定：Python 的 random、NumPy、PyTorch、CUDA。漏掉任何一处，两份完全相同的代码就会跑出不同结果。

② 配置记录

超参数、数据路径、批大小、划分比例写进文件或一个字典——不许散落在代码各处，更不许只存在记忆里。

③ 版本管理

代码版本、环境版本、数据版本。三者缺一，结果就无法追溯到任何东西上。

它换来了什么

任何人（包括三天后已经忘了自己改过什么的你）都能复核的结果。

1.5.2 覆盖每一处随机源

import random, numpy as np, torch

def set_seed(seed: int = 42) -> None:
    random.seed(seed)                    # Python 内置随机
    np.random.seed(seed)                 # NumPy
    torch.manual_seed(seed)              # PyTorch（CPU）
    torch.cuda.manual_seed_all(seed)     # 全部 GPU

set_seed(42)
a = torch.rand(3)
set_seed(42)
b = torch.rand(3)
print(torch.equal(a, b))   # True —— 同一种子，同一批数
两次固定种子还是不一致？ 说明别处还有随机：种子设在数据生成之后、某处 NumPy 没固定，或者用了带 shuffle 与多 worker 的 DataLoader。按可能性排序，逐条排查——不要从头重写。

1.5.3 可复现不承诺什么

固定种子只保证同一环境内等价。跨不同 GPU 型号、库版本或 CPU 架构出现微小数值差异是正常的、无法避免的。正确的做法是把环境与设备写在数字旁边——而不是悄悄只留下最好的那一次。

1.6 AI 使用边界与过程留痕

本课程期待你使用 AI 工具。它们在解释概念、起草代码、查 API 名字上确实很好用。但有一件它们做不到：为结果负责——而你的名字签在提交物上，那正是你要承担的东西。

可以做不可以做
解释你卡住的概念提交你无法逐行解释的代码
生成草稿代码，然后自己读、自己测、自己改用 AI 的结论替代你自己的验证
查 API、查版本、查报错信息把 AI 生成的内容当作自己的原创成果
起草文档框架与测试用例用 AI 编造结果、日志或输出

1.6.1 协同记录

每一次影响你工作的 AI 使用都要写进 AI_USE.md，编号并注明日期。关键部分不是提示词，而是你发现的错误。

## 协同记录 #01 · 2026-09-15

**我想要的**：用 autograd 手写一次梯度下降。

**AI 给了什么**：一段 w -= lr * w.grad 的循环。

**我发现了什么问题**：
- 没有在每步前清零梯度 -> 梯度被累加，损失震荡；
- 形状 (3,) 与 (3,1) 混用，广播后结果和预期不同。

**我怎么改的**：加 w.grad.zero_()；统一 reshape(-1, 1)。

**结论**：骨架可用，但两处错误必须自己发现
—— 这是本课程的核心要求。
评分规则 只写「AI 帮了我」的记录不得分。记录必须指出 AI 在哪里错了、你是怎么发现的——因为那部分只有你能产出。AI 协同记录占形成性考核 50 分中的 10 分。

1.7 常见误区与排查清单

检查清单
  • 先读报错再动手修。 导入失败在没有反证之前，都是路径问题。
  • 一个项目一个环境。 建好当天就导出并提交 environment.yml。
  • 检查设备并写进报告。 只用 CPU 可以，「我没查」不行。
  • 四处随机源都要固定。 Python、NumPy、PyTorch、CUDA。
  • 先基线，后改进。 先拿一个笨数，永远如此。
  • 一次只改一个变量。 否则你的「对比」只是一则轶事。
  • README 里要有可复现命令。 写不出命令，这个结果就不算数。
  • 记录失败，不只记录成功。 那才是你动过手的证据。

1.8 小结与练习

五条要点
  1. AI 应用开发是端到端流水线——问题定义、数据、建模、评估、部署、运维——模型只是其中一环。
  2. 技术栈分四层（应用、模型、数据、基础设施）加两条贯穿线（MLOps、负责任 AI）。出问题先给它定层。
  3. 能力用「能交付什么」定义。岗位矩阵里每一行都是你能展示的东西，不是你能背出来的东西。
  4. 环境要一次配好：隔离环境、验证过的 PyTorch、记录下来的设备、入了版本库的仓库。
  5. 可复现性三要素——种子、配置、版本。缺任何一项，你报出的数字都无法被追溯与复核。

练习 1 · 给它定层（必做）

  1. 把下列各项归入四层中的某一层，并说明归哪类角色负责：一个 FastAPI 接口、一个 conda 环境文件、一次分层抽样划分、一条 P95 时延告警、一个 Docker 镜像、一份数据卡片。
  2. 挑其中两项，各写一句话：如果这一层坏了，用户会先看到什么现象？

练习 2 · 翻译一条招聘要求，并审计一次 AI 回答（必做）

  1. 找一条真实的 AI／机器学习工程岗位招聘要求。
  2. 把每一条要求改写成一个「交付物」（例如「能为 X 搭数据管道」「把推理时延降低过 Y」）。
  3. 逐条对照 1.3.2 的能力矩阵。你选的这条招聘里，出现最多的能力维度是哪一个？完全缺失的又是哪一个？
  4. （+5 加分）让一个 AI 工具列出「AI 工程师」应具备的能力，再逐条与带日期的来源核对——在招岗位、官方能力框架、公司工程博客。做出一张三列表：说法、来源、结论。至少标出一条过时或缺乏依据的说法并说明你为什么不采信它。这正是本课程期待的核查能力，也是本次练习中唯一被认可的 AI 使用方式。

练习 3 · 种子实验（必做）

  1. 建好环境后，带 set_seed(42) 跑两次种子演示脚本，再完全不带种子跑一次。
  2. 把三行真实输出贴进报告。不要手打。
  3. 逐个去掉随机源（先 random，再 NumPy，再 PyTorch），记录是哪一步去掉之后，两次固定种子的运行第一次不再相等。
  4. 用你自己的实测差异，写两三句话解释为什么本课程要求固定种子。

练习 4 · 建立记录仓库（必做）

  1. 按实验 0 的目录结构建一个公开 Git 仓库：README.md、environment.yml、每周一个目录、AI_USE.md。
  2. 把 README 写成「别人不用问你任何问题就能重建环境并跑起脚本」的程度。
  3. 换一个目录重新克隆，严格照自己的 README 操作一遍，记录每一处你不得不靠猜的地方。

练习 5 · 问题定义单草案（必做）

为你真的想做的项目写一页问题定义单，必须包含五件事：

  1. 目标用户，写得越具体越好；
  2. 待解决的问题，一句话说清；
  3. 你确实能拿到的数据，以及从哪来（一个 URL 或一个具名来源，不是「网上的」）；
  4. 你打算用来宣称成功的指标；
  5. 失败判据——什么情况会让你承认这个想法不成立。
