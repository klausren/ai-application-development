Introduction to AI Application Development

⏱ Weekly 180-min integrated session · this plan covers the Lecture Part, 90 min (L1–L5) 📚 Chapter 1.1–1.5 🎯 Module 1 · AI Application Development Foundations (W1–4) 🧩 Lesson Plan ID: LP-W1-A 🌐 English

1. Learning Objectives

Knowledge

  • Distinguish traditional software development from AI application development, and explain why the difference matters for testing
  • Draw the six-step pipeline from idea to production and say what happens at each step
  • Place a given technology into one of the four stack layers (application / model / data / infrastructure)
  • Name the three core roles and map them onto the course weeks where each is trained
  • State the three pillars of reproducibility — seed, config, version — and why all three are needed
  • State what this course permits and forbids in the use of AI tools, and what must be recorded

Skills

  • Read a job advertisement for an AI role and translate each requirement into a deliverable
  • Create an isolated conda environment and verify the PyTorch version and compute device in three lines
  • Write a set_seed() helper that fixes Python, NumPy, PyTorch and CUDA random sources
  • Draft a problem-definition sheet: users, problem, available data, intended metric, failure criteria
  • Keep an AI collaboration trace that records where the AI was wrong, not merely that it was used
Attitudes Two habits start this week and last all term. First, a result is not a result until one command in a README reproduces it. Second, AI assistance is welcome, unexplained AI assistance is not. The course also opens with a professional-aspiration note: the goal is not to call a library, but to build something a real user can rely on — and that is what "科技报国、职业理想" means in practice, one working deliverable at a time.

4. Key Activity Design

Activity 1 · Draw the Pipeline First (L1, p5)

Before the pipeline slide is shown, ask the class to list, in order, what has to happen between "someone has an idea for a useful AI feature" and "a user gets an answer". Collect answers on the board, then reveal the six steps and mark which ones the class omitted. Data and operations are almost always missing — which is exactly the week's thesis: the model is one link, not the chain.

Activity 2 · Which Role Is This? (L2, p10)

Read five one-line job requirements aloud ("build the data pipeline for 20 million rows", "cut P95 inference latency from 800 ms to 200 ms", "decide whether this can ship given the bias audit"). Students assign each to a role and then to a course week. The debrief: every requirement is phrased as a deliverable, and none of them is "knows the algorithm".

Activity 3 · Diagnose the Broken Import (L3, p14)

Run the self-check script in the wrong environment so it raises ModuleNotFoundError. Nobody may install anything for one minute — first, someone must answer: which interpreter is this shell actually using, and how would you find out? The lesson (read the error, locate the interpreter, then act) is worth more than the fix.

Activity 4 · Two Runs, Same Code (L4, p19)

Run the seed demonstration twice on the projector: first with set_seed(42), then without it. The seeded outputs are identical to the last digit; the unseeded ones differ. Ask what the second run proves about a published result that has no seed, and let the class arrive at "nobody can check it" themselves.

Activity 5 · A Good Trace vs a Bad Trace (L4–L5, p21)

Show two AI-collaboration entries. One says "the AI helped me write a gradient-descent loop, it worked well." The other names two concrete bugs the AI produced and how each was found. Ask which one is gradeable and why. Land the rule: the value of a trace is the error in it, because that is the part only you could have found.
