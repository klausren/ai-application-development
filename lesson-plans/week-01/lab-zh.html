1. 教学目标

知识目标

  • 解释隔离环境防的是什么，以及 environment.yml 里应该有什么
  • 说出环境自检必须证明的三件事：版本、设备、显存
  • 解释固定种子为什么让两次运行可比，以及有哪些随机源必须一起固定
  • 说出可复现标准的三个组成部分：种子、配置、版本
  • 说出一条合格的 AI 协同记录必须包含什么

能力目标

  • 建立 conda 环境、安装 PyTorch，并用一个脚本验证计算设备
  • 同一脚本带种子与不带种子各跑一次，用原始输出证明两者的差别
  • 导出并提交环境配置，让别人能重建你的环境
  • 建立 Git 实验记录仓库，写清目录结构与命名约定
  • 推送 M1 里程碑：三个题目提案、PROJECT_PLAN.md 与 DEVLOG.md v0
素养目标 把工作台当作交付物的一部分。「我这里能跑」说的是你的机器，不是你的结果。从今天起，你报出的每一个数 都要有一条 README 里的命令能把它跑出来；同时，任何 AI 协助都要在记录里看得见——**包括 AI 错在哪里**。

2. 重点与难点

类别内容处理策略
重点隔离环境与 environment.yml；三行设备自检；固定种子对比实验；记录仓库目录结构；实验 0 的五项交付物教师逐段演示（3–5 分钟一段），学生随后复现；每段结束必须先把结果写进 report.md 再进入下一段
难点torch.manual_seed 之后 run1 与 run2 仍可能不同；「没有 GPU」是可接受的答案但「我没查」不是；报告里的输出必须是真跑的而不是手打的种子：跑完脚本后逐个去掉随机源，看哪一次结果变了；GPU：现场展示一台无 GPU 机器也能产出合法的 check_env.txt（device: cpu）；诚信：对比「粘贴的真实输出」与「手打的输出」，说明手打等于编造

4. 关键活动设计

活动 1 · 先读报错，再动手修（实验 A，p22）

当 import torch 失败时，前两分钟不许重装任何包：必须先口头回答三个问题——这个终端用的是哪个解释器、当前激活的是哪个环境、包装在哪里。养成一个反射：导入失败在没有反证之前，都是「路径问题」而不是「包没装」。

活动 2 · 先预测第二次运行（实验 B，p24）

运行之前，每人先写下自己预期 run1、run2、no-seed 三行是否相同，然后再跑。对 run2 感到意外的学生人数，正好等于从没检查过自己结果是否可复现的人数。

活动 3 · 找出漏掉的随机源（实验 C，p24）

如果有学生两次运行不一致，全班一起诊断，而不是教师直接改好。按可能性排序：种子设在数据生成之后、numpy 没固定、用了带 shuffle 与多 worker 的 DataLoader。诊断清单比修好那一处更有价值。

活动 4 · 换目录重新克隆（实验 D，p25）

每人把自己的仓库克隆到另一个目录，只照着自己的 README 从 environment.yml 重建环境。绝对路径、缺失文件、README 里根本没写「怎么跑」——这些问题会立刻暴露，比任何检查清单都更有说服力。

活动 5 · 三个提案，而不是一个想法写三遍（实验 E，p26）

两人互读对方的三个提案，各自指出其中一个「大概率做不完」的并说明原因。这不是批评，而是写三个的意义所在。最后五分钟教师逐人确认选题与裁剪清单。
