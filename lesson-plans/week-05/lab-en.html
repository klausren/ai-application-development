1. Learning Objectives

Knowledge

  • State the five steps of a training loop and the exact call for each, from memory
  • Explain why gradients accumulate when zero_grad() is missing, and what that does to the effective step size
  • Explain why CrossEntropyLoss must receive raw logits, and what a second softmax does to the gradient
  • Distinguish the three failure regimes of a learning rate — exploding, converging, crawling — from the shape of the loss curve
  • Explain why the initial weights must be identical across every compared run

Skills

  • Write a reusable train() function with a per-epoch log, using the five-step loop correctly
  • Run a 3 × 3 optimizer × learning-rate grid with only two variables changing
  • Plot loss and accuracy curves (shared axes plus small multiples) and read the convergence speed and stability off them
  • Name the winning combination with a number, a comparison and a mechanism — not a preference
  • Write a four-line "does not converge" log: symptom → hypothesis → evidence → conclusion
  • Push the M5 capstone milestone (training loop + comparison table) before the lab ends
Attitudes Treat tuning as experimental design, not luck. Every claim about a hyper-parameter must trace to a run you performed, with one variable changed and everything else pinned. An honest "this combination failed, and here is the curve" earns more credit than an unexamined success.

4. Key Activity Design

Activity 1 · Write It Before You Type It (Lab A, p20)

Every student writes the five steps on paper, in order, before opening the notebook. The instructor walks the room and reads them; students who omit step 1 are asked to reproduce the accumulating-gradient snippet (11.78 → 23.58 → 35.39) and then explain what a three-times-too-large gradient does to the step size. Typing without writing first turns the loop into copy-paste.

Activity 2 · One Number, Two Softmaxes (Lab A, p20)

Students print CrossEntropyLoss()(logits, y) and CrossEntropyLoss()(softmax(logits), y) side by side. Both look plausible; neither raises an error. The instructor then trains both for 30 epochs on the projector and lets the accuracy curves separate. Nobody forgets the rule "pass raw logits" afterwards.

Activity 3 · Predict Before You Run (Lab C, p21)

Before starting the grid, each student writes down three predictions: which optimizer wins at 1e-3, which combinations fail to converge, and whether 1e-1 hurts every optimizer equally. Then they run. Comparing the predictions with the nine results is what turns a mechanical sweep into calibration — and the "momentum amplifies at 1e-1" result usually surprises the room.

Activity 4 · Twelve Curves, Four Figures (Lab D, p22)

The first attempt is always nine curves on one axes, and it is always unreadable. The instructor requires small multiples: one figure per optimizer, three learning rates each. Students immediately see the within-optimizer comparison (the learning rate effect) separately from the between-optimizer comparison (the update-rule effect) — which is the whole point of a factorial design.

Activity 5 · Four Lines for a Failing Run (Lab D–E, p24)

Each student writes the debugging log using the fixed labels — symptom / hypothesis / evidence / conclusion — for their worst run. The evidence line must cite the control run that confirms the hypothesis. The instructor's standard: if the first hypothesis is not about the learning rate, the log goes back. This is exactly the format the CS-style debugging records in later weeks reuse.
